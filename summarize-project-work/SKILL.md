# 專案工作會報總結

## 目標

將一個專案的可驗證成果整理成繁體中文會報。只報告目前專案資料支持的事實；不要把 commit 標題、計畫、推測或單次摘要直接當成完成證明。這個 skill 是唯讀分析流程，除非使用者另行要求，不修改專案、不產生任務包、不 commit，也不 push。

## 不可省略的證據範圍

完整盤點下列來源，並在輸出中說明沒有找到的項目：

- 目前工作樹與受 Git 追蹤的檔案：入口、主要模組、設定、腳本、產出物與刪除狀態。
- Git：目前分支、工作樹狀態、遠端、提交範圍、每個候選任務的相關提交與目前淨內容。
- README、設計文件、規格、變更紀錄、部署／操作文件與其他文件索引。
- 測試檔、測試命令、CI 設定與可安全執行的驗證；沒有測試時明確記錄「目前專案未找到測試檔」。
- 可執行原始碼的實際控制鏈：入口 → 核心流程 → 輸出或副作用；只讀摘要、圖譜或文件不足以替代原始碼。

若專案適用 codebase-memory，先確認索引；未索引就先建立索引，再優先使用 get_architecture、search_graph、trace_path、get_code_snippet 做程式碼探索。圖譜可能過期，必須回到目前 Git 檔案、實際引用與必要的 targeted check 交叉驗證。找字串、README、設定、腳本與非程式檔時可使用 rg／rg --files。

## 分析流程

### 1. 建立現況基線

先讀取並保留以下結果：

~~~
git status --short --branch
git remote -v
git log --all --date=short --pretty=format:'%h|%ad|%an|%s'
git log --all --stat --oneline
rg --files
~~~

再按目錄讀 README、原始碼、測試與文件。確認目前檔案是否仍存在、是否由提交保存、是否只是被 README 提及。不要因 timeout、warning、stopped 或摘要看起來成功，就宣稱任務完成。

### 2. 還原實際控制鏈

對每個可能形成任務的功能：

1. 找到入口、主要函式／類別、資料流、輸出與錯誤處理。
2. 讀完整的關鍵函式與其直接呼叫者／被呼叫者；必要時用 trace_path 追到測試或輸出端。
3. 將文件描述與目前程式逐項對照，記下已實作、只文件化、文件落後或互相矛盾之處。
4. 對腳本、CLI、背景服務或外部整合，分開記錄「程式存在」與「本次是否有實際執行證據」。

### 3. 合併 Git 修改

以使用者可理解的成果邊界分組，不以 commit 數量分組。可使用：

~~~
git log --follow -- <path>
git show --stat --summary <commit>
git show <commit> -- <path>
git diff <before>..<after> -- <path>
~~~

合併同一目標的新增、修正、重構、文件同步與驗證提交。合併提交只作為整合證據，不重複計算。被 revert、刪除、未合併或只存在於歷史而不在目前工作樹的內容，不列為目前已完成工作；若它能解釋範圍或風險，再放到判斷依據的待確認說明。

### 4. 判定完成狀態

使用下列狀態，必要時加上層級限定：

| 狀態 | 使用條件 |
|---|---|
| 已完成 | 目前工作樹仍有對應成果，控制鏈或文件鏈完整，且 Git／驗證證據足以支持使用者要求的範圍。 |
| 部分完成 | 主要成果存在，但仍有缺口、文件／程式不一致、失敗的關鍵驗證，或只完成其中一段控制鏈。 |
| 待確認 | 只有計畫／commit 宣稱、成果已刪除或撤銷、缺少關鍵檔案，或目前資料不足以證明完成。 |

「沒有測試檔」不自動等於未完成；它代表測試覆蓋與執行驗證必須在狀態或判斷依據中標成「待確認」。同樣地，文件型任務可在文件現況與提交證據充分時標為已完成，但不要虛構 runtime 驗證。

### 5. 形成會報任務

每項任務都要有單一清楚的成果主題，例如「建立可增量更新的 Codebase Atlas 工作流」或「建立本機影片轉文字流程」，不要寫成「修改 A、B、C」。將下列內容放進同一任務：

- 目的與使用者可感知的結果。
- 相關程式、文件、設定、腳本與產出格式。
- 同一目標的多個提交及其目前留下的淨結果。
- 測試、CI、手動驗證、限制與未證實範圍。

不要逐筆翻譯 commit；不要把所有小修正拆成孤立任務；不要把「新增過但後來刪掉」寫成現行能力。

## 證據寫法

每個結論至少提供一種目前狀態證據，並盡量搭配一種歷史或驗證證據：

- 目前檔案：使用相對路徑，必要時加行號、函式／類別名稱或 section。
- Git：使用短 hash、日期與能說明意圖的提交範圍；不要只貼 commit 標題。
- 測試／驗證：貼實際命令與結果；待確認要說明缺少哪一項證據。
- 文件對照：指出 README／文件與實際檔案一致或不一致之處。

把「原始碼事實」「候選／分類／計數」「判斷」分開。若只能從間接線索推得，使用「依目前資料推定」並把它標為待確認；不可用肯定語氣補足空白。

## 固定輸出格式

除非使用者指定其他格式，使用以下結構，並以繁體中文輸出：

~~~
# 專案實際完成工作會報

## 盤點範圍與總結
- 專案／分支／盤點截止點：
- 已讀來源：原始碼、Git、README、測試、文件（逐項說明實際找到的內容）
- 整體判斷：
- 主要限制或待確認：

## 主要任務

### 1. <任務名稱>

**任務名稱**：<成果導向名稱>

**任務摘要**：<1–3 句，說明完成了什麼、解決什麼問題>

**任務清單**：
- <合併後的子成果>
- <程式／文件／驗證項目>

**完成狀態**：<已完成／部分完成／待確認；必要時附層級限定>

**判斷依據**：
- 目前檔案事實：<path、symbol、文件段落>
- Git 證據：<commit hash、日期、目前淨結果>
- 測試／驗證：<命令與實際結果，或明確說明沒有>
- 限制／待確認：<不可由資料證明的部分；沒有則寫「無」>

## 待確認與未列為完成的項目
- <只列會影響完成判斷的缺口；沒有則寫「無」>

## 主管版精簡任務清單
- <任務名稱>：<一句話成果>（<狀態>）
- <任務名稱>：<一句話成果>（<狀態>）
~~~

任務順序以主管易讀為準：先列主要交付或影響最大的工作，再列支援性文件、維護與清理。若同一任務含多層狀態，清楚分開「實作／文件已完成」與「執行驗證待確認」，不要用單一綠燈掩蓋缺口。

## 最終自檢

交付前逐項確認：

- 每個任務都能回指目前檔案與至少一段 Git 或驗證證據。
- 相關提交已合併成成果，不是逐筆翻譯或只重述標題。
- 已刪除、revert、未合併、計畫中與目前成果已分開。
- README、測試、文件與原始碼的矛盾已揭露。
- 沒有測試／執行證據的地方已標示待確認，沒有把空白當成通過。
- 主管版清單只保留可報告的成果，不塞入探索過程、命令細節或未證實推測。
