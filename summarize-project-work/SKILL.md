# 專案進度回報

把專案的實際工作整理成可以直接填進專案管理系統的內容。系統裡每個專案底下是一串子任務，每個子任務有 0–100% 的進度（100 = 開發完成），可以附上一則進度回報，寫當天做了哪些事。大多數專案就是一層子任務；少數專案會先分一層群組（例如前端、後端），子任務掛在群組底下。子任務會隨著開發增加，例如做到一半要寫操作手冊、要對模型做微調。

唯讀：不改專案、不 commit、不 push。

兩條核心原則：
- **以成果歸類，不以 commit 歸類**：同一目標的新增、修正、重構、文件、測試提交，歸進同一個子任務；被 revert、刪除或後來整批被取代的內容，不算進度。
- **以目前狀態為準**：commit 標題、計畫、README 宣稱都只是線索；成果要在目前的 HEAD 或工作樹裡找得到，才算數。

## 1. 先定範圍

| 項目 | 預設 |
|---|---|
| 期間 | 今天（`'<今天> 00:00'` 到現在）；使用者說「這週」「從 X 號開始」時照著改 |
| Repo | 目前目錄；同一個專案分散在多個 repo（例如前端、後端各一個）時，一起盤點，歸進同一個專案 |
| 作者 | 使用者本人（`git config user.email` 和常見的別名） |
| 現有子任務 | 使用者貼了系統裡現有的子任務和百分比，就以它為準；沒貼就由你提一份建議清單（見第 3 步） |

## 2. 收集證據

每個 repo 先跑：

~~~
git status --short --branch
git log --since='<起> 00:00' --until='<迄> 23:59' --author=<作者> --date=short --pretty=format:'%h|%ad|%s' --no-merges
git log --since='<起> 00:00' --until='<迄> 23:59' --author=<作者> --name-only --pretty=format:'--%h' --no-merges
~~~

`--since`／`--until` 要寫到時刻。只寫日期的話，git 會套用現在的時刻，當天較早的提交就會漏掉。

接著依每個候選成果的狀況決定要查多深：

- **一定要做**：確認成果還在 HEAD（關鍵檔案或函式還在、沒有被 revert 或刪除）；看期間結束後有沒有提交推翻它（`git log <最後一個提交>..HEAD -- <path>`）；記下對應的測試和文件。
- **有疑點才深挖**：標題寫得比 diff 大、提交裡出現 WIP／revert／fix 的連鎖，或是文件宣稱的功能找不到程式時，讀 `git show <hash> -- <path>` 和實際程式。
- **驗證**：測試或 build 便宜又安全時，就實際跑一次；要連實際環境、要很久或有副作用的就不跑，在回報裡寫明「未驗證」。
- **工作樹還沒 commit 的變更**：算進當天的進度，回報裡註明「未 commit」。
- **repo 外的事實**（部署、實機測試、主管驗收、模型訓練結果）：只有使用者提供或文件有記錄時才寫。

## 3. 對到子任務

**有現有子任務時**：把每項成果歸到既有的子任務，名稱照抄系統裡的，不要自己改名；有群組的專案保留原本的群組。這期間沒有動到的子任務不用列。

**對不到既有子任務時**：成果屬於另一種工作（操作手冊、模型微調、部署、資料整理），而不只是既有子任務的一部分時，列成「建議新增子任務」，用結果命名，並附上它的起始百分比。只是既有子任務的修正或延伸，就歸進去，不要另開。

**沒有現有子任務時**：提一份建議清單。
- 預設只有一層子任務；只有專案本身分成前端、後端這類獨立部分（通常是不同 repo 或不同部署）時，才加一層群組。
- 子任務用結果命名（「上傳支援 2GB 檔案」），不用動作清單命名（「修改 A、B、C」）。瑣碎的修正併進相關的子任務，或歸成一項「維護與清理」。

## 4. 估百分比

百分比要能說出依據，依下列順序取：

1. **有範圍清單時**：計畫文件、issue checklist、atlas 任務包或 TODO 列出了這個子任務要做哪些項目，就用「已完成項目 ÷ 全部項目」計算。
2. **有現有百分比、沒有清單時**：從原本的百分比往上調，調整幅度要對應這期間新完成的項目；除非成果被 revert 或刪掉，否則不往下調。
3. **兩者都沒有時**：照下表的階段估，並標成「建議值」：

| 階段 | 建議值 |
|---|---|
| 只有探勘、設計或雛形 | 10–20 |
| 主要功能實作中，有一部分可以運作 | 30–60 |
| 功能寫完，還缺測試、串接或修正 | 70–80 |
| 程式和測試都完成，只差驗收或合併 | 90 |
| 開發完成（在 HEAD、測試或 build 通過、沒有已知缺口） | 100 |

沒有實際驗證證據的子任務，最多填 90，並在回報裡寫明還沒驗證什麼。文件類子任務（操作手冊）看章節是否寫齊、內容是否和目前程式一致；微調類子任務看訓練與評估結果，沒有結果就停在實作階段的建議值。群組的百分比通常由系統自己彙總；使用者要求手動填寫時，就用子任務的平均，並註明算法。

## 5. 寫進度回報

每個有變動的子任務寫一則回報：
- 1–3 行，白話描述這期間完成了什麼、效果是什麼，不貼 commit 標題或 hash。
- 有卡點或下一步時加一行；沒有就不寫。
- 量化只用查得到的數字（測試數從 140 增加到 175、驗證集準確率從 82% 提高到 88%），不要估算。

## 輸出格式

直接輸出在對話裡，不要存成檔案；使用者會一筆一筆複製，貼進系統。所以回報內文用純文字，不加粗體、連結或程式碼標記，貼上後才不會留下符號。使用者沒指定時，照下面的格式輸出，證據放最後：

~~~
# <專案>：<期間> 進度

- <子任務>：<舊 %> → <新 %>（<依據：清單 3/5／階段估計，建議值>）
  回報：<今天做了哪些事>
  下一步：<可省略>

- ...

## 建議新增子任務
- <名稱>：<起始 %>（<依據>）
  回報：<這期間做了哪些事>

## 待確認
- <對不到子任務的成果、無法驗證的項目；沒有就省略這一節>

## 證據
- <子任務>：<關鍵檔案路徑>；<hash 範圍>；<驗證指令與結果>
~~~

有群組的專案，在子任務上面加一層 `## <群組>`。沒有舊百分比時就省略「<舊 %> →」；沒有建議新增的子任務時，就省略那一節。

## 交付前自檢

- 每則回報都能在「證據」裡回指目前的檔案和提交或驗證。
- 每個百分比都寫了依據；用階段估計的都標了建議值。
- 已刪除、revert、被取代的內容沒有算進進度；沒有跑過的驗證沒有寫成通過。
- 有現有子任務時，名稱照抄系統裡的；新增的只放在「建議新增子任務」。
