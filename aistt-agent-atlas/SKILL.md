# AISTT_Agent Codebase Atlas

本專案日常工作的單一自帶進入點與路由器。它自帶完整的判斷規則——不需要再去讀
其他獨立的流程文件。

## 進入

1. 保留使用者原始的請求內容。
2. 讀一次 `../../../docs/aistt_agent_index.md`，用一句白話確認這個專案是做什麼
   的。
3. 只從索引挑出相關的模組文件——不要全部讀完。如果不熟悉該區域，先看模組地圖
   再往下鑽。
4. 依意圖分流：**了解類**（解釋、定位、可行性、歸屬、行為確認、審查、重現、
   剖析、CI 失敗、風險評估）→ 走「調查」；**變更類**（任何程式碼編輯）→ 走
   「變更」；混合/不明確 → 先調查再決定。
5. 把結論往後傳遞；除非需要尚未取得的資訊，否則不要在後續步驟重複讀索引或
   模組文件。

## 調查（唯讀）

從 Atlas 加上必要的最少程式碼回答問題；把已確認的事實與假設/未知分開講。絕不
編輯——如果需要修正，取得使用者同意後才交給「變更」。依問題性質套用對應的
判斷方式：除錯 = 重現 → 依可能性排序假設 → 二分排查；審查 = 對照擁有模組與
邊界模組讀 diff；開放式設計問題 = 一次問一個問題、每題附建議答案，並對照索引與
「架構決策」表——若提案牴觸已記錄的職責/邊界，或想重開已記錄的決策，要明確
點出來。

## 變更（任何編輯）

先判斷變更等級，再決定投入的力度：

- **T0（瑣碎）**（無邏輯變更、可逆、單一檔案）：一行 Before/After；略過計畫檔；
  只跑最相關的一項檢查。
- **T1（一般）**（範圍侷限、可逆、診斷明確）：若有低成本的測試切入點就加一個
  focused test；編輯原始碼前先寫暫存計畫
  `docs/changes/planning/{{DATE}}-{{SLUG}}.md`（`{{DATE}}` 為今天的本地日期，
  ISO `YYYY-MM-DD`）。
- **T2（困難/高風險）**（非同步/有狀態的 bug、跨模組、外部 API、不可逆、效能
  退化、診斷不確定）：完整規格；同樣要寫計畫檔；通常需要走 Decision Gate。

**硬性下限**：不可逆、跨模組、外部 API、遷移類的工作至少是 T2。使用者若明確要求
「快一點/仔細一點」可以尊重，但不能低於這個下限。

**Before / After 關卡**（唯一的確認介面）：
- **Before**：目前的狀態，以及為什麼需要這個變更——若是 bug，要寫出診斷出的
  根本原因——用白話描述。
- **After**：變更完成後會變成什麼樣子，以及要怎麼驗證。

T1/T2 等級，編輯任何檔案前要等使用者明確確認。T0（瑣碎、可逆、單一檔案）等級，
說明一行 Before/After 後可以直接進行，事後回報——因為即使 Before 判斷錯了，這個
等級的變更也是可逆的。

**Decision Gate** —— 當變更會改動模組邊界、外部 API、屬於不可逆／遷移類，或
有兩個以上可行方案時：先確認提案是否牴觸或想重開索引「架構決策」表裡記錄的
內容——若是，要明確點出並確認使用者確實要重開這項決策。接著呈現「背景 /
選項（A/B 附取捨）/ 建議」，等使用者選定後才進入 Before/After。跨模組決策記錄到
索引的「架構決策」表；模組內決策記錄到該模組文件的「已知風險」。

編輯後依變更等級做對應的驗證；驗證結果一律要出現在回報中——檢查沒過絕不能宣稱
完成。**宣稱完成前，必須明確自問**：這次變更有沒有改到模組邊界、歸屬，或外部
API／契約？有的話，現在就更新受影響的 Atlas 文件，當作這次收尾的一部分——不要
留到下次才想起來。接著把計畫檔搬到
`docs/changes/completed/{{DATE}}/{{SLUG}}.md`，並在當天的
`docs/changes/completed/{{DATE}}/summary.md`（當日工作摘要）補上一行，註明
Atlas 是否已更新或本次不需更新。

## 回報與交付

- 回報詳細度：**只用白話文**——使用者對話回報中不出現模組名稱、檔案路徑或
  程式碼片段。（模組文件與變更計畫檔屬開發者產出物，不受此限。）
- 產出後處理：**commit 並 push**——完成變更後主動在目前分支 commit 並 push，
  不需再詢問（依使用者全域指示）。
- 除非使用者明確要求整個重建，否則不要重新執行 Codebase Atlas 初始化流程。
