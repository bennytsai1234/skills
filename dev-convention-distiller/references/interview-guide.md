# 訪談指南

訪談是雙來源萃取的另一半,專門挖**程式碼看不到的東西**：協作慣例、決策理由、踩雷經驗、以及哪些做法使用者想帶到未來。

掃描看「做了什麼」,訪談看「為什麼、是否刻意、是否想複用」。兩者交叉才能濾出真正的可遷移準則。

## 提問的四大方向（依價值排序）

### 方向一：協作流程慣例（價值最高,務必深挖）

這是可遷移性最強的一類——跟語言、框架完全無關,搬到任何專案都成立。也是程式碼最看不出來的（程式碼只留下結果,留不下「你怎麼跟 agent 互動」)。

追問範例：

- 「你跟 AI agent 開發這個專案時,有沒有要求它『動手前先做某件事』？例如先說明計畫、先列出要改的檔案、先寫測試？」
- 「開發過程中,你反覆糾正過 agent 哪些行為？哪些事它常做錯、你每次都要提醒？」
- 「你會限制 agent 一次改動的範圍嗎？還是放手讓它大改？」
- 「有沒有哪些情況,你希望 agent 停下來問你、而不是自己決定？」
- 「agent 寫完之後,你習慣怎麼驗證？有固定的檢查流程嗎？」

每挖到一條,追問關鍵的可遷移性問題：**「這個習慣,你會想在下個完全不同的專案也沿用嗎？」**

### 方向二：決策原則背後的「為什麼」

掃描能看到「做了什麼」,訪談補上「為什麼這樣做」——有理由支撐的慣例才值得變成準則。

對照式提問（把掃描線索拿來確認):

- 「我注意到你的錯誤處理都走 ⟨某模式⟩。這是你刻意的慣例,還是這個專案剛好這樣？」
- 「你的相依好像一律用建構子注入,沒看到 service locator。這是你的原則嗎?為什麼?」
- 「測試命名都用 ⟨某格式⟩,這是你會堅持的風格嗎?」

確認是「刻意慣例」後,再問可遷移性:「換個語言/框架,你還會堅持這個原則嗎?」

### 方向三：踩雷與避坑清單

使用者反覆踩過的雷,沉澱成「叫 agent 別這樣做」的準則,實用價值極高。

追問範例：

- 「開發這個專案,有沒有踩過什麼雷,後來變成你的『以後一定要注意』？」
- 「有沒有哪種寫法/做法,你現在會主動避免、也希望 agent 避免？」
- 「有沒有哪次 agent 的某個決定害你後來很痛苦,你不想再發生？」

### 方向四：溝通與產出偏好

使用者希望 agent 怎麼跟自己互動、產出長什麼樣。這類偏好高度個人化且跨專案穩定。

追問範例：

- 「你希望 agent 用什麼語言回應你?（這位使用者預設繁體中文,可確認)」
- 「你喜歡 agent 回得精簡直接,還是詳細解釋?」
- 「agent 產出文件/註解時,你有偏好的風格嗎?」
- 「你希望 agent 在不確定時直接給建議,還是先列選項讓你選?」

## 對照式提問：訪談與掃描的接點

訪談最有威力的用法,是拿掃描結果去驗證。標準句式：

> 「我在程式碼裡看到 ⟨掃描發現的模式⟩。我想確認三件事：① 這是你刻意的慣例嗎?② 為什麼這樣做?③ 你會想在下個專案也這樣嗎?」

三個問題一次釐清「是否刻意 / 決策理由 / 可遷移性」,效率最高。

## 處理「講一套做一套」的落差

如果使用者宣稱某慣例,但掃描顯示程式碼裡並不一致——這是雙來源萃取最有價值的時刻。直接、坦白地點明：

> 「你提到習慣 ⟨X⟩,不過我在程式碼裡看到有些地方並沒有這樣做（例如 ⟨具體處⟩)。想跟你確認:是這個習慣還在養成中、還是有些情況會例外?這會影響我要不要把它寫成準則。」

釐清後再決定:是寫成準則（使用者確實想堅持,只是還沒貫徹)、加上條件（有明確例外情境)、還是不寫(其實沒那麼堅持)。

## 節奏控制

- 每輪最多 3-5 題。
- 先問方向一（協作流程),它價值最高且最不可能從程式碼補。
- 使用者已答到的就跳過,別重複確認。
- 通常 2-3 輪收斂。若 3 輪後仍大量缺口,可能是專案本身慣例不明確,或使用者還沒形成穩定的個人原則——這時誠實告知「可萃取的可遷移準則有限」,不要硬湊。

## 收斂標準

訪談足夠的標準是:對每一條打算寫進 CLAUDE.md 的準則,都能回答——

1. 它是刻意的慣例,還是專案巧合?（從訪談得知）
2. 程式碼是否支持?（從掃描得知）
3. 搬到完全不同的專案還成立嗎?（可遷移性)
4. 使用者是否想帶到未來?（從訪談得知）

四題都有答案,才算這條準則的證據足夠。
