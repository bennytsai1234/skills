# 專案掃描指南

掃描的目的不是理解「這個專案做什麼」,而是蒐集**可遷移個人準則**的線索。看的是「刻意養成的慣例」,不是「這個專案的功能細節」。

## 掃描順序（由粗到細）

### 1. 先看設定檔（訊號最濃)

設定檔最能透露「跨專案會帶著走的工具鏈偏好」,優先看：

- **格式化 / Lint 設定**：`.editorconfig`、`.eslintrc*`、`prettier` 設定、`.csharpierrc`、`analyzers` 設定、`dart analysis_options.yaml` 等。這些直接是可遷移的編碼風格偏好。
- **測試框架線索**：測試相關的 package 引用、測試專案結構、CI 設定中的測試步驟。透露「測試習慣」。
- **專案 / 套件設定**：`*.csproj`、`package.json`、`pubspec.yaml`、`Directory.Build.props` 等。看的是**慣例**（例如是否一律啟用 nullable、是否統一某 lint 等級),不是具體套件清單（具體套件是專案特有,不可遷移）。
- **CI/CD 設定**：build/test/deploy 的步驟順序,可能透露工作流程慣例。

### 2. 看目錄結構的「重複模式」

不是記錄「有哪些資料夾」（那是專案特有),而是找**一致的組織慣例**：

- 是否每個功能模組都用同一套子結構？
- 命名是否有穩定規則（檔名、資料夾名的大小寫與用詞慣例）？
- 測試檔放哪、怎麼命名、跟原始碼的對應關係？

這些「一致性本身」才是可遷移的線索。

### 3. 抽樣讀程式碼,找「反覆出現的寫法」

不需讀完整個專案。抽幾個代表性檔案,找**跨檔案重複的編碼決策**：

- **錯誤處理**：是否有固定模式（統一用某種 Result 型別？統一在某層 try/catch？例外往上拋還是就地處理？）。
- **相依管理**：相依怎麼進來的（建構子注入？靜態存取？service locator？）。是否一致。
- **非同步寫法**：async/await 的慣例、是否避免某些反模式。
- **命名風格**：變數、方法、類別的命名慣例是否一致。
- **註解 / 文件慣例**：是否有固定的文件字串風格。

## 分辨「可遷移線索」與「專案特有雜訊」

掃描時持續用這把尺過濾：

| 看到的東西 | 歸類 | 處理 |
|---|---|---|
| 統一啟用 nullable reference types | 可遷移線索 | 記下,訪談時確認是否刻意 |
| 用了 EF Core 連 PostgreSQL | 專案特有雜訊 | 忽略,不入準則 |
| 所有 service 都建構子注入 | 可遷移線索 | 記下 |
| `OrderService` 的具體邏輯 | 專案特有雜訊 | 忽略 |
| 測試一律命名 `Method_Scenario_Expected` | 可遷移線索 | 記下 |
| 資料表 schema | 專案特有雜訊 | 忽略 |

## 掃描的產物

掃描結束時,在心裡（或對話中簡述）整理出一份「候選線索清單」,每條註明：

- 線索內容（看到的慣例）
- 證據（在哪些檔案看到、是否一致）
- 初步可遷移判斷（強 / 弱 / 待訪談確認）

這份清單是步驟 2 訪談的素材——尤其用來做「對照式提問」（把看到的模式拿去跟使用者確認是否刻意、是否想帶到未來）。

## 重要提醒

- 掃描只能看到「做了什麼」,看不到「為什麼」「是否想複用」。**絕不可只憑掃描就把線索寫成準則**,一定要經過訪談驗證。
- 看到的一致性也可能是「框架逼的」而非「使用者刻意的」。例如某框架本來就強制某種結構——這種不算使用者的可遷移準則,訪談時要分辨。
- 證據有限時（使用者只貼片段),坦白告知掃描涵蓋範圍有限,並更倚重訪談。
