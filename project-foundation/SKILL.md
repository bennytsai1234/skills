# Project Foundation

Create the smallest durable project-document system that helps humans and coding agents work in the repository without duplicating the same facts in several places.

This skill is for repository documentation foundation, not product ideation. `project-genius` handles pre-code product requirements/prototyping; this skill handles a real repository's working documentation.

Read `references/document-contract.md` before creating or reorganizing files.

## Target shape

Prefer this root documentation surface:

```text
AGENTS.md
README.md
DEVELOPMENT.md
DESIGN.md          # only when the repository has a real UI/design system

docs/
  architecture.md  # only when justified
  <atlas files>    # generated by codebase-atlas
  changes/         # formal Atlas work history, when present
  ...              # other long-lived project docs
```

Do not create files merely to fill the shape. Optional files must have real content and a clear owner.

## Existing repository workflow

1. Read applicable global/project instructions.
2. Inventory current root docs and `docs/` content before writing.
3. Read existing README, AGENTS/CLAUDE guidance, development/setup docs, architecture/design docs, and any existing atlas index.
4. Classify useful content by responsibility using `references/document-contract.md`.
5. Preserve correct project-specific facts. Merge duplicate guidance into one canonical location rather than copying it again.
6. Update stale wording when repository evidence proves the current state changed.
7. Remove or relocate a document only when its useful content has been preserved elsewhere and the old file is clearly redundant/superseded. Do not delete unrelated ecosystem-required files or unknown documents just to make the root visually minimal.
8. Create missing required foundation files with repository-grounded content.
9. Decide whether `DESIGN.md` and `docs/architecture.md` are justified; skip them when they would be empty or speculative.
10. When meaningful source code exists, build or refresh Codebase Atlas as the final navigation step. Prefer refresh when an existing atlas has usable provenance; rebuild only when its boundaries/provenance are unreliable.
11. Validate links and eliminate contradictory duplicate instructions.

## New repository workflow

For a new or nearly empty repository:

1. Create only the foundation that current facts support.
2. Create `AGENTS.md`, `README.md`, and `DEVELOPMENT.md` with the known project conventions and commands; use explicit TODOs for genuinely undecided project-specific values rather than inventing them.
3. Create `DESIGN.md` only when a UI/design system or confirmed prototype already exists.
4. Do not create `docs/architecture.md` before there is a real cross-component system to describe.
5. Do not create Codebase Atlas for an empty skeleton. Once meaningful source structure exists, run `codebase-atlas` initialization.

## Architecture decision

`docs/architecture.md` is optional.

Create or keep it only when the repository benefits from a high-level view that the module map should not carry, such as:

- multiple deployable processes/services;
- cross-module runtime orchestration;
- important state ownership across DB/Redis/files/queues/memory;
- external systems that shape runtime behavior;
- deployment topology such as load balancers, active/active instances, workers, leaders, or GPU services.

Skip it when Atlas module maps plus README/DEVELOPMENT already make the system understandable.

Architecture should stay short and current: system overview, critical runtime flows, data/state ownership, external systems, deployment. Do not duplicate module-level file routes from the atlas.

## Design decision

`DESIGN.md` means product visual/design system guidance for coding agents: visual direction, tokens, typography, layout, components, interaction conventions, and do/don't guidance that actually exists in the product.

Do not use root `DESIGN.md` for one feature proposal or backend implementation plan. If the repository has no meaningful UI/design system, omit it.

## Atlas handoff

Project Foundation does not duplicate engineering-map generation rules.

After foundation docs are coherent:

- no atlas + meaningful source -> run `codebase-atlas` initialize;
- existing atlas + ordinary drift -> run `codebase-atlas` refresh;
- structurally invalid atlas -> run `codebase-atlas` rebuild after stating why.

The atlas remains the code-navigation map. Foundation docs remain project guidance and high-level context.

## Delivery

Follow current human instructions and repository `AGENTS.md` for commit/push behavior. Report which documents were created, merged, moved, removed, or intentionally omitted and why.
