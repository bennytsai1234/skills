# Dev Flow

把目前專案對照下列標準路線，找出是否偏航；有偏航就拉回最近的合理階段，沒有偏航就直接讓目前工作繼續。只處理會讓開發順序、環境或 AA 架構偏離標準的問題，不當成一般 code review。Dev Flow 只管已經開始寫 Code 之後，不要求先完成固定需求階段，因為需求可以持續調整。

## 開發資源規則

公司專案預設最終支援 AA + Redis。開發用哪套 DB/Redis 由申請狀態決定，完整規則以 `cota` skill 的「開發預設與申請狀態」為準：

- 尚未申請或資源未到位 → 本機 DB / LocalDB + 本機 Redis。
- 已申請且資源到位 → 直接用測試 DB 與公司 Redis：test 帳號建表，申請帳號以執行身分讀寫 DB、連 Redis；新申請專案用當下最新版 Redis 連線程式碼／CotaRedis 套件。建表成功不等於執行帳號已有讀寫權限。

下面的階段是能力與驗證的進展，不是強制等待順序；已取得的測試資源隨時可用，不要求先走完本機替代階段。

## 標準路線

### 1. 本機開發（起步 / 除錯）

`Trial + 依申請狀態的 DB/Redis + 單 Web`

- 沒有公司帳號、網路或資源時，仍能 build、啟動並開發核心功能。
- Trial 只負責在 Development 提供目前使用者與權限；業務程式不綁死 Trial。
- 本機 DB、Redis、API 位址等設定不寫死在業務程式；公司套件的內建連線與執行身分驗證沿用公司規格，不額外手刻帳密。
- 需要跨 Web 共用的狀態放 Redis 或 DB，不只放單一 Web 記憶體。
- 同時處理同一份資料的兩個請求不互相覆蓋或重複執行；重送的操作不產生重複結果。
- 核心功能不依賴某一台 Web 的本機檔案。

### 2. 本機 AA 驗證

核心功能能在單 Web 跑通後進入本機 AA；身分驗證未接入時仍可用 Trial。AA 行為驗證與新的公司服務整合分開做。

**第一次**：開兩個 Web（可先不掛 HAProxy），逐項確認：

- A 產生的共享狀態，B 看得到。
- 登入、Session、暫存與權限切到另一台後正常。
- 背景工作、排程或一次性工作沒被兩台重複執行。
- 只在單機有效的 lock、記憶體 cache 或暫存沒造成錯誤。
- 檔案沒有只存在其中一台 Web。
- 任一 Web 重啟或退出後，另一台仍能處理核心流程。

**之後**：AA 基礎完成的公司專案，把 `本機 HAProxy → Web A + Web B → 共用 Redis + DB` 固定成日常開發環境，讓 session、antiforgery、跨 instance 狀態每天都被驗證，不拖到最後才發現大量功能不支援 AA。單 Web 只留給專案初期與快速除錯。本機 HAProxy 是開發驗證工具，不取代公司正式的 Load Balancer。專案不以 AA 為目標，或 AA 基礎未完成時，雙 Web 與 HAProxy 不是必要條件。

本機 AA 通過只代表程式的 AA 行為已初步驗證，不代表公司 AA 已通過。

### 3. 公司服務整合

依申請與資源到位狀態接入，不把「先完成全部本機 AA」當成前置條件。

- 資源還沒發下來：可以先加套件、Adapter、介面、設定欄位或整合程式碼，但 Development 預設仍走本機路徑，缺少公司帳號、endpoint、憑證或網路不能讓本機無法 build 或啟動。沒有實際資源可測時只能判為「已準備、尚未驗證」。
- 資源到位：核對建表帳號、執行帳號權限與最新版連線程式碼。
- 以目前程式碼與設定判斷接入狀態，不從 Git commit 猜順序；先後關係會改變結論而現況看不出來時才問使用者。
- 多個公司服務混在一起、無法判斷錯誤來源時，先縮小到單一變因，不要求為形式重寫專案。

**身分驗證**：把「業務需要的目前使用者」和「使用者從哪裡登入」分開。Development 由 Trial、公司整合由實際身分來源（員工入口網簽章、AD、AD + OTP、Keycloak 或專案指定方式）產生同一組「目前使用者 / 員工編號 / 角色 / 權限」，業務功能只依賴這一組。Dev Flow 不決定用哪種身分來源；Cota 平台細節查 `cota` skill。

### 4. 公司環境驗證

確認實際部署組合：`Load Balancer → Web A + Web B → 公司 Redis + 公司 DB`，加上實際身分驗證、HTTPS、監控與健康檢查。重點是公司資源、網路、設定與部署方式是否和已完成的程式設計相容；不要把部署環境問題誤判成需要重寫業務功能。

## 四類偏航

| 類別 | 典型情況 | 校正方向 |
|---|---|---|
| 開發環境 | 未申請或資源未到位，Development 卻沒有公司 Redis／正式 DB 就無法啟動；未申請就強迫接公司資源；AA 基礎未完成或不以 AA 為目標，卻被迫同時啟動雙 Web、HAProxy 等非必要元件。使用已申請的測試資源不算偏航 | 依申請狀態選資源；AA 基礎未完成用單 Web，完成後日常用本機雙 Web + HAProxy |
| 程式設計 | 重要狀態只在單一 Web 記憶體；排程在 AA 下被兩台重複執行；核心資料只寫 Web 本機檔案；Trial、AD、入口網簽章等登入方式散落在業務邏輯 | 只修會讓 AA 或環境切換失效的部分，不做無關重構 |
| 公司服務接太早 | 核心功能變更與新的公司服務整合同時引入，分不出是業務還是環境問題；帳號、endpoint、權限或憑證未取得就讓公司套件成為本機開發的必要條件 | 本機路徑保持可用；未驗證的整合標為尚未驗證 |
| 一次混入太多變因 | 多個新公司服務、AA 問題與業務修改混在一起，錯誤來源無法定位 | 以目前程式狀態一次只隔離一個真正影響判斷的變因；不檢查 commit 數量或要求固定 commit 順序 |

## 執行方式

收到明確的 Dev Flow 呼叫後，唯讀查看程式碼、設定、測試與可取得的執行證據，判斷目前最接近哪個階段，檢查四類偏航。只列有證據或會直接阻塞下一步的項目，不因最佳實務或未來可能需要而製造工作；沒有偏航就直接說可以繼續。不修改程式碼、設定、部署，也不申請資源。

## 輸出

沒有偏航時，只說目前最接近的階段和可以繼續。有偏航時用以下五段，保持簡短：

- **現在在哪**：目前最接近的階段。
- **偏離哪裡**：已成立的偏航。
- **為什麼**：會造成的實際問題，不講抽象最佳實務。
- **怎麼拉回來**：最小校正方式，不延伸成全面重構計畫。
- **下一步**：目前最值得做的一步；必要時再列一個可並行的工作。
