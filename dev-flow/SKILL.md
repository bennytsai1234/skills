# Dev Flow

把目前專案對照下列標準路線，找出是否偏航；有偏航就拉回最近的合理階段，沒有偏航就直接讓目前工作繼續。

不要把 Dev Flow 當一般 code review。只處理會讓開發順序、環境或 AA 架構偏離標準的問題。

## 標準開發路線

公司專案預設最終都要支援 AA + Redis。

1. **本機開發**
   `Trial + 本機 DB / LocalDB + 本機 Redis + 單 Web`
2. **本機 AA 驗證**
   `Trial + 共用本機 DB + 共用本機 Redis + Web A + Web B`
3. **公司服務整合**
   將本機替代資源逐步換成實際公司資源。
4. **公司環境驗證**
   `公司 DB + 公司 Redis + 實際身分驗證 + Load Balancer + HTTPS + AA`
5. **正式環境**

Dev Flow 只管已經開始寫 Code 之後；不要要求先完成固定需求階段才開始判斷，因為需求可以持續調整。

## 1. 本機開發

平常開發固定以這個環境為基準：

```text
Trial
+ 本機 DB / LocalDB
+ 本機 Redis
+ 單 Web
```

要求：

- 沒有公司帳號、公司網路、公司 DB 或公司 Redis 時，仍能 build、啟動與開發核心功能。
- Trial 只負責在 Development 提供目前使用者與權限所需資訊；業務程式不要綁死 Trial。
- DB、Redis、API 位址與憑證放在設定，不寫死在業務程式。
- 重要狀態不要只放在單一 Web 的記憶體；需要跨 Web 共用的狀態放 Redis 或 DB。
- 兩個請求同時處理同一份資料時，不要互相覆蓋或重複執行。
- 同一個操作被重送時，不要產生不該出現的重複結果。
- 不要讓核心功能依賴某一台 Web 的本機檔案。
- 功能還沒完成時，優先把本機核心流程做通，不要先把主要精力移去接公司服務。

## 2. 本機 AA 驗證

核心功能已能在本機單 Web 跑通後，再開兩個 Web：

```text
Web A + Web B
      ↓
共用本機 Redis + 共用本機 DB
```

仍使用 Trial 與本機資源，先只驗證 AA，不同時引入公司環境變因。

依專案功能檢查：

- A 產生的共享狀態，B 是否看得到。
- 登入、Session、暫存與權限切到另一台 Web 後是否正常。
- 背景工作、排程或一次性工作是否被兩台重複執行。
- 只在單機有效的 lock、記憶體 cache 或暫存是否造成錯誤。
- 檔案是否錯誤地只存在其中一台 Web。
- 任一 Web 重啟或退出後，另一台是否仍能處理核心流程。

需要驗證實際分流或故障切換時，再加入本機 Load Balancer；不必把它變成平常單 Web 開發的必要條件。

本機 AA 通過，只代表程式的 AA 行為已初步驗證，不代表公司 AA 已通過。

## 3. 公司服務整合

核心功能與本機 AA 已有可用基礎後，再接公司資源。

公司資源還沒發下來時：

- 可以先加入套件、Adapter、介面、設定欄位或整合程式碼。
- Development 預設仍走本機 DB、本機 Redis、Trial。
- 不要讓缺少公司帳號、endpoint、憑證或網路導致本機不能 build 或啟動。
- 沒有實際資源可測時，只能判斷為「已準備、尚未驗證」，不要宣稱整合完成。

公司資源到位後，再切換實際資源並驗證。

不要從 Git commit 猜接入順序。以目前程式碼與設定狀態為準；如果先後關係會直接影響判斷而現況看不出來，再詢問使用者。

如果多個公司服務已混在一起而無法判斷錯誤來源，先縮小到單一變因，不要求為了形式重寫整個專案。

### 身分驗證

把「業務需要的目前使用者」和「使用者從哪裡登入」分開。

Development：

```text
Trial
 ↓
目前使用者 / 員工編號 / 角色 / 權限
 ↓
業務功能
```

公司整合：

```text
實際身分來源
 ↓
目前使用者 / 員工編號 / 角色 / 權限
 ↓
同一套業務功能
```

實際公司身分來源可能是 CotaPortal、AD、AD + OTP、Keycloak 或專案指定方式。Dev Flow 不自行決定哪一種；依專案與公司規格判斷。若環境中有 `cota` skill，涉及 Cota 平台細節時查該 skill，不在 Dev Flow 重複平台規格。

## 4. 公司環境驗證

本階段才確認實際部署組合，例如：

```text
Load Balancer
    ↓
Web A + Web B
    ↓
公司 Redis + 公司 DB

+ 實際身分驗證
+ HTTPS
+ 監控 / 健康檢查
```

此階段重點是驗證公司資源、網路、設定與部署方式是否和已完成的程式設計相容，不要把部署環境問題誤判成需要重寫業務功能。

## 四類偏航

### 開發環境偏航

例如：

- Development 沒有公司 Redis 就無法啟動。
- 本來可以用本機 DB，卻被正式 DB 連線綁死。
- 平常開發被迫同時啟動雙 Web、Load Balancer 或其他非必要正式元件。

校正方向：恢復 `Trial + 本機 DB + 本機 Redis + 單 Web` 的可開發路徑。

### 程式設計偏航

例如：

- 重要狀態只存在單一 Web 記憶體。
- 排程在 AA 下會被兩台重複執行。
- 核心資料只寫到 Web 本機檔案。
- Trial、AD、CotaPortal 等登入方式直接散落在業務邏輯中。

校正方向：只修正會讓 AA 或環境切換失效的部分，不做無關重構。

### 公司服務接太早

以下兩種都要注意：

- 核心功能還沒在本機完成，就先投入公司服務整合，導致無法分辨是業務功能問題還是環境問題。
- 公司帳號、endpoint、權限或憑證還沒取得，就讓公司套件變成本機開發的必要條件。

若功能已完成但資源尚未取得，可以先準備整合程式碼；只要本機路徑仍可正常使用，這不算偏航。未實際驗證的部分必須標為尚未驗證。

### 一次混入太多變因

目前程式同時混入多個新公司服務、AA 問題與業務修改，導致錯誤來源無法定位時，判為偏航。

校正方向：以目前程式狀態縮小問題範圍，一次只隔離一個真正影響判斷的變因。不要為了流程形式檢查 commit 數量或要求固定 commit 順序。

## 執行方式

收到明確的 Dev Flow 呼叫後：

- 唯讀查看目前程式碼、設定、測試與可取得的執行證據。
- 判斷目前最接近標準路線的哪個階段。
- 檢查四類偏航；只列有證據或會直接阻塞下一步的項目。
- 不要因為「最佳實務」「未來可能需要」而製造修改工作。
- 有偏航時，提出能回到標準路線的最小校正方式。
- 沒有偏航時，直接說目前可繼續，不硬找問題。
- 只有關鍵先後資訊無法從目前專案判斷，而且會改變結論時，才詢問使用者。

不要修改程式碼、設定、部署或申請資源；Dev Flow 只負責診斷與校正建議。

## 輸出

預設只使用以下五段，保持簡短：

### 現在在哪

指出目前最接近哪個階段。

### 偏離哪裡

列出已成立的偏航；沒有就寫「沒有明顯偏航」。

### 為什麼

只解釋會造成的實際問題，不講抽象最佳實務。

### 怎麼拉回來

提出最小校正方式，不延伸成全面重構計畫。

### 下一步

只給目前最值得做的一步；必要時再列一個可並行工作。
