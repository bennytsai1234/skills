# Dev Flow

## 核心原則

- 只依可查證證據判斷，不靠對話印象或設定名稱推定完成。
- 分開標記：**已確認／尚未確認／卡點**。
- 正式目標未另行指定時，預設 **AA + Redis**。
- 本機成功、Cota 成功、AA 成功是不同結論。
- 外部資源等待期間，本機開發與申請可並行。
- 找出「最後一個確定能跑的版本」，再決定前進或回退。
- 不為了最佳實務主動重構；只處理目前會阻塞或造成錯誤的問題。

## 開發流程

```text
需求
↓
本機可跑版本
↓
功能可用
↓
雙 Web 測試
↓
接公司服務
↓
公司 AA 驗證
↓
上線準備
↓
正式環境
```

### 本機可跑版本

預設使用：

```text
單 Web
+ Trial 登入／授權模式（只限 Development）
+ 本地 DB / LocalDB（已授權的實際資料）
+ Docker Redis
```

要求：

- 沒有公司網路也能 build、啟動與測試。
- 公司 endpoint、帳號、憑證不能是本機啟動必要條件。
- 業務邏輯與公司套件或服務有明確邊界。
- Trial 只可放在 Development profile；測試與正式環境仍依實際登入／授權規則驗證。
- 本機功能與流程驗證只使用本地 DB 中已授權的實際資料，不使用自行產生的 mock、fixture、seed 或虛構資料。
- 若沒有可合法放在本機使用的實際資料，標為卡點並準備核准的備份／匯出資料；不要自行造資料繼續宣稱功能已通過。
- 公司服務尚未取得時，不用假回應或模擬服務冒充通過；受影響功能標為尚未驗證，其他不依賴它的本機工作可繼續。
- 若專案沒有 Trial 模式，不自行臆造；查專案既有的本機登入方式，或將 Trial 標為尚未確認。

### 功能可用

先使用本地 DB 的實際資料完成業務流程、資料契約、設定邊界與核心測試。切換本機服務與公司服務時，盡量只替換連接方式，不重寫業務流程。

### 雙 Web 測試

本機功能穩定後才測：

```text
Web A + Web B
      ↓
共用 Redis + DB
```

依專案實際功能檢查：

- 登入狀態與暫存資料是否一致。
- A 寫入的資料或狀態，B 是否看得到。
- 背景工作或排程是否被兩台重複執行。
- 兩台切換後，連線、檔案與狀態是否仍能使用。
- 重啟後是否能恢復。

本機雙 Web 通過不代表公司 AA 已通過。

### 接公司服務

一次只接一項：

```text
Local DB → CotaDB
Docker Redis → CotaRedis
登入／身分
權限
其他公司服務
監控／HA
```

每接一項都確認：

- 公司資源是否已取得。
- 本機是否仍可執行。
- 是否有實際驗證證據。
- 是否有上一個正常版本可以退回。

某項失敗就退回上一個已通過的項目，不把多項半成品一起繼續往前推。若 CotaRedis 或公司 DB 只能使用公司內部資源且尚未取得，不要用 Docker Redis 或 LocalDB 的成功代替公司整合證據。

## 遇到問題怎麼辦

### 卡住

公司 DB、Redis、帳號、權限、憑證或網路尚未取得。

→ 留在本機可跑版本或功能可用階段繼續開發，申請流程與需要的公司服務盤點並行。

### 混亂

本機與 Cota 混在一起，已無法判斷錯誤來源，或專案還沒有按 AA + Redis 建立可驗證的版本。

→ 停止繼續接公司服務，回到本機可跑版本。

### 接公司服務失敗

某一項 Cota 整合失敗。

→ 退回上一個正常項目，只處理這一項，不同時加入其他公司服務。

### 雙 Web 失敗

單 Web 正常，但兩個 Web 出現狀態、重複執行、登入、檔案或重啟問題。

→ 回到雙 Web 測試階段修正，不重寫業務功能；先找出哪些資料或工作不能只放在單台 Web。

## 退回本機版本

既有專案整合混亂時：

1. 保留目前 commit、設定、錯誤與套件證據，建立可回復點。
2. 先移除或隔離本機啟動路徑中的 Cota 公司套件、設定與公司服務；保留業務功能與資料契約。
3. 恢復：
   `單 Web + Trial + Local DB + Docker Redis`
4. 通過 build、啟動、核心功能與實際資料測試。
5. 再測雙 Web。
6. 最後逐項接回公司服務。

目的是找回最後一個確定能跑的版本，不是刪除業務功能或全面重寫。若直接移除公司套件會造成編譯失敗，先把它隔離，讓本機版本可以建置與啟動。

## 判斷流程

執行本 Skill 時：

1. 找出最後一個確定能跑的版本。
2. 判斷目前是正常前進、卡住、混亂、接公司服務失敗或雙 Web 失敗。
3. 找出真正卡點，區分資源等待、環境差異、程式問題與驗證不足。
4. 只提出下一個最小可驗收動作。
5. 列出可以並行的工作，例如本機功能開發、雙 Web 問題盤點、已授權實際資料準備與公司資源申請。
6. 若使用者想跳步，說明缺少的驗證與實際風險。

## 輸出

預設只回答：

- **目前階段**
- **已確認**
- **卡點／尚未確認**
- **下一步**
- **可並行**
- **跳步代價**

不要每次重新講完整流程。
